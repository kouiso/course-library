# Release and rollback runbook

## Before activation

1. The gift is TypeScript for survey respondents; Taskapp is a paid product and must not be added to this gift library. Confirm the exact TypeScript distribution inventory/version and the MyASP survey-response/invitation settings. Keep all original Drive files unchanged. Do not interpret the shared phrase as an individual survey identity check.
2. Verify the target Cloudflare account, plan, R2/Worker/rate-limit eligibility, limits and budgets. Confirm the CI account/repository billing state. No paid plan changes, paid CI runners, extra grants, or remote workload is authorized by this runbook.
3. Choose a stable HTTPS hostname. Replace `APP_ORIGIN` and the R2 bucket placeholder in `wrangler.jsonc`. Keep `APP_MODE=production`; do not publish the localhost configuration. Select account-unique rate-limit namespace IDs to avoid counters shared with another Worker.
4. Prefer the existing authorized Cloudflare connector for initial manual provisioning and deployment; it supports the relevant Worker and R2 API operations without a new persistent credential. Actual connector write scopes are untested. A separate persistent deployment credential is only a future GitHub CD option requiring explicit approval and verified scope. Keep R2 managed public access and custom public bucket domains disabled. No CORS or presigned download URLs are required. Keep the public application hostname on the Worker, not the bucket.
5. Through a separately approved secure step, prepare `ACCESS_PHRASE_SHA256` and `SESSION_SECRET` (at least 32 random bytes encoded as 43+ base64url characters). Use protected secret storage and non-logging secret input; never command-line literal values, terminal output, or Git. Ordinary `wrangler secret put` deploys immediately, so it is not a preparation-only command. Use an explicitly approved version-only secrets upload when the target supports it, or provide the secrets during the first separately approved deployment. See [the initial setup guide](SETUP.md). The access phrase and PDF opening password are separate.
6. Do not reconnect unrelated pending authentication requests or enable Cloudflare Git auto-deployment. Secure credential creation and CI activation need explicit action-time authorization.

## Prepare a material release

1. Copy only confirmed distribution sources into an ignored private working directory outside this repository. Never move, modify or delete Drive originals.
2. Make PDF **distribution copies** with AES-256 open-password encryption in an approved secure step. Use a separate owner password, preserve useful print/copy permissions, and protect password input from process arguments/history/logs. One version may share a PDF opening password. No encryption command is automated here because real credential entry remains pending.
3. Open every encrypted copy with its expected password and confirm failure with a wrong/missing password. Check useful copy/print and representative Mac PDF readers. Windows/WSL and course source execution need their own verification. Do not infer compatibility from synthetic PDFs.
4. Build the TypeScript PDF bundle from the encrypted distribution PDFs and inspect its exact member names. Do not add Taskapp code, books or bundles to this library. Add any TypeScript supplementary code only if independently confirmed as part of the gift. Keep hashes, sizes, source inventory and release evidence in a private operator report, never in the public repository when identifying information is sensitive.
5. Upload to a **new immutable** private prefix such as `releases/typescript/CONFIRMED-VERSION/`. Never overwrite active release objects. Validate every expected object and byte length/checksum against the private release report before updating the manifest. Preserve earlier release prefixes for rollback.
6. Update the approved TypeScript collection version, safe filenames, object prefix and `synthetic` flag in `src/manifest.ts`. Keep `survey-gift` and `survey-respondents` policy restrictions. Do not add a paid-product collection or reuse product prefixes/filenames. Record the MyASP/invitation and release review privately before enabling both release approval flags. The current false flags and synthetic release deliberately block production and `npm run release:ready`. Update catalogue descriptions and verification notes truthfully. Public metadata must contain no private inventory identifiers.
7. Run `npm ci` and `npm run check` at the exact candidate commit, then perform staging/private edge checks on direct anonymous GET/HEAD/Range, wrong/expired cookies, missing objects, cache headers, successful downloads and mobile/desktop browser behaviour. No public access grants are needed for R2.

## CI/CD activation (not performed)

Every checked-in workflow is `workflow_dispatch` only. None runs on push, PR, issue or schedule events, so a PR that adds a workflow never starts it; `tests/automation.test.mjs` fails if a trigger is added. No Actions run has been requested. Before first manual execution, verify the actual plan and free usage limits and review this configuration. It uses `ubuntu-latest`, no self-hosted/larger runners, no artifact storage, and no cache storage. Concurrency is fixed for the library and cancellation is disabled, so verification and deployment from different releases cannot race.

Only if recurring GitHub CD is separately authorized, confirm the actual token policy and secure destination before creating or storing a credential. Legacy `Workers Scripts Edit/Write` is account-scoped; do not describe it as limited to one named Worker. New individual-Worker Editor authorization is documented separately, but its actual availability and policy on the target account remain unverified. After that approval, place the credential and account ID in the `production` environment secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Set environment variable `CLOUDFLARE_SETUP_VERIFIED=true` only after plan/limit, bucket privacy, secrets, hostname, and material verification are complete. The optional deploy job uses the same `github.sha` as verification and refuses a placeholder production configuration. Environment-level approval protection should be configured separately if authorized; this runbook creates no grants or credentials.

## Repository automation (manual)

These workflows read issue/PR data with the run's `GITHUB_TOKEN` only, never check out or run code from a PR head, and use no paid service or new credential. Their decisions live in `scripts/automation/` and are unit-tested in `tests/automation.test.mjs` with a fake API, so no test issue or comment is written to this public repository.

- `body-format.yml` (inputs: `issue`/`pr` and number): checks the five issue headings (背景 / 今どこまで / 次にやること / 誰の判断待ち / 完了条件) or the PR headings (概要 / 変更内容 / 関連Issue with `Closes #n` or `Refs #n`; the account default template's 概要・背景・妥協点 / やったこと / 関連 Issue are accepted). It keeps one marked comment, updates it to OK after a fix, and skips bots, draft PRs and `alert` issues.
- `issue-heading-fix.yml` (input: issue number): changes `###` to `##` and `####` to `###` outside code blocks, and edits the issue only when the text would change.
- Templates: `.github/ISSUE_TEMPLATE/request.yml` makes the five checked headings required. A repository-local issue folder replaces the account-wide forms from `kouiso/.github` for this repository only (checked read-only on 2026-10-30), so the account contact link is copied into `config.yml`. No local PR template is added: the account default (関連 Issue / 概要・背景・妥協点 / やったこと / Before・After / checklist) already applies and the body check accepts its headings.
- `pr-settings.yml` (input: PR number; run it after a PR is opened or reopened): assigns the human author. Bot PRs are skipped, and the step uses `continue-on-error` so a failed assignment does not stop later steps.
  The next step adds labels: branch `feature/`·`feat/` → feature, `bugfix/`·`fix/` → bugfix, `hotfix/` → hotfix, `chore/`·`refactor/` → chore, `docs/` → documentation, `release/` → release; paths `docs/`, `README.md`, `*.md` → documentation, `wrangler.jsonc`, `tsconfig.json`, `worker-configuration.d.ts`, `.github/`, `.githooks/` → config, `package.json`/`package-lock.json` → dependencies. Labels already on the PR are never removed. GitHub creates a missing label name on first use.
- `secret-scan.yml` (no input; choose the PR branch or default branch in "Use workflow from"): downloads gitleaks 8.30.1, refuses it unless the pinned sha256 matches, and scans the full Git history with redacted output. It reads code only, never issue/PR/comment text, and needs only `contents: read`. The run has not been executed yet; the first run may report existing synthetic test values that need an allowlist decision.

Switching any of them to automatic events is a separate decision: change its `on:` block, update this section, the README delivery note and the workflow test together.

## Deploy and verify

1. Select a reviewed commit and the optional deployment input only after the above prerequisites are met. Verification must pass for that same SHA before deployment.
2. Record the Git SHA, content manifest version, Cloudflare Worker version ID and previous Worker version ID in private release evidence. Use the stable entry URL in the newsletter; MyASP configuration remains unchanged.
3. Repeat the anonymous/authenticated/cache-isolation checks through the real HTTPS hostname. Confirm `r2.dev` and public bucket domains remain disabled. A code test cannot establish account-level privacy or billing settings.

## Roll back

1. If credentials or materials leaked, rotate the access phrase and session signing secret through the approved secure flow; rollback alone does not revoke sessions or downloaded files.
2. Revert the manifest/application to the previous known-good reviewed commit through normal review and deploy after same-commit verification, or use the approved Cloudflare Worker version rollback for an urgent application rollback. Match the Worker version to its embedded material manifest.
3. Keep the previous immutable R2 objects available. Validate the stable URL and authentication/download/cache behaviour again. Do not delete releases until the recovery/retention decision is separately approved.

Reference: [Workers R2 API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/), [rate-limit scope and accuracy](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), [GitHub external CI/CD](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/).
