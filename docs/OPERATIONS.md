# Release and rollback runbook

## Before activation

1. The library distributes two kinds of material: the free TypeScript gift for survey respondents, and paid products for buyers (currently `redmine-clone` and `task-app`). A paid product is never part of the free gift; it is a separate collection with its own phrase, release prefix and approval flag (see [Distribute a paid product](#distribute-a-paid-product)). For the gift, confirm the exact TypeScript distribution inventory/version and the MyASP survey-response/invitation settings. Keep all original Drive files unchanged. Do not interpret the shared phrase as an individual survey identity check.
2. Verify the target Cloudflare account, plan, R2/Worker/rate-limit eligibility, limits and budgets. Confirm the CI account/repository billing state. No paid plan changes, paid CI runners, extra grants, or remote workload is authorized by this runbook.
3. Choose a stable HTTPS hostname. `wrangler.jsonc` already holds the production values (`APP_ORIGIN` is `https://course-library.kouiso.workers.dev`, the R2 bucket is `course-library-materials`); change them only when the hostname or bucket changes. Keep `APP_MODE=production`; do not publish the localhost configuration. Select account-unique rate-limit namespace IDs to avoid counters shared with another Worker.
4. Prefer the existing authorized Cloudflare connector for initial manual provisioning and deployment; it supports the relevant Worker and R2 API operations without a new persistent credential. Actual connector write scopes are untested. A separate persistent deployment credential is only a future GitHub CD option requiring explicit approval and verified scope. Keep R2 managed public access and custom public bucket domains disabled. No CORS or presigned download URLs are required. Keep the public application hostname on the Worker, not the bucket.
5. Through a separately approved secure step, prepare every secret listed in [Required production settings](SETUP.md#本番に必須の設定値): `ACCESS_PHRASE_SHA256` (SHA-256 digest of the access phrase as 64 lowercase hex characters), `SESSION_SECRET` (at least 32 random bytes encoded as 43+ base64url characters), and `BASIC_AUTH_USER` / `BASIC_AUTH_PASS` (required in production; the outer Basic site gate stays in place after distribution starts). The phrase secret of a paid product is separate and is covered in [Distribute a paid product](#distribute-a-paid-product). A missing or malformed value makes the whole site return 503 without a visible cause. Use protected secret storage and non-logging secret input; never command-line literal values, terminal output, or Git. Ordinary `wrangler secret put` deploys immediately, so it is not a preparation-only command. Use an explicitly approved version-only secrets upload when the target supports it, or provide the secrets during the first separately approved deployment. See [the initial setup guide](SETUP.md). The access phrase and PDF opening password are separate.
6. Do not reconnect unrelated pending authentication requests or enable Cloudflare Git auto-deployment. Secure credential creation and CI activation need explicit action-time authorization.

## Prepare a material release

1. Copy only confirmed distribution sources into an ignored private working directory outside this repository. Never move, modify or delete Drive originals.
2. Make PDF **distribution copies** with AES-256 open-password encryption in an approved secure step. Use a separate owner password, preserve useful print/copy permissions, and protect password input from process arguments/history/logs. One version may share a PDF opening password. No encryption command is automated here because real credential entry remains pending.
3. Open every encrypted copy with its expected password and confirm failure with a wrong/missing password. Check useful copy/print and representative Mac PDF readers. Windows/WSL and course source execution need their own verification. Do not infer compatibility from synthetic PDFs.
4. Build the TypeScript PDF bundle from the encrypted distribution PDFs and inspect its exact member names. Do not put files of a paid product into the gift bundle or under the gift prefix; a paid product is released as its own collection (see [Distribute a paid product](#distribute-a-paid-product)). Add any TypeScript supplementary code only if independently confirmed as part of the gift. Keep hashes, sizes, source inventory and release evidence in a private operator report, never in the public repository when identifying information is sensitive.
5. Upload to a **new immutable** private prefix such as `releases/typescript/CONFIRMED-VERSION/`. Never overwrite active release objects. Validate every expected object and byte length/checksum against the private release report before updating the manifest. Preserve earlier release prefixes for rollback.
6. Update the approved TypeScript collection version, safe filenames, object prefix and `synthetic` flag in `src/manifest.ts`. Keep `survey-gift` and `survey-respondents` policy restrictions. Do not turn the gift into a paid-product collection, and do not reuse the prefix or filenames of a product for the gift (`validateManifest` requires the prefix `releases/<id>/<version>/` and filenames that start with `<id>-`). Record the MyASP/invitation and release review privately before enabling both release approval flags. The current false flags and synthetic release keep the survey gift closed in production; `npm run release:ready` still passes while at least one collection (gift or paid product) is ready, and blocked collections stay closed in production. It fails when no collection is ready, when the approved gift cannot be distributed, or when `validateManifest` throws. Update catalogue descriptions and verification notes truthfully. Public metadata must contain no private inventory identifiers.
7. Run `npm ci` and `npm run check` at the exact candidate commit, then perform staging/private edge checks on direct anonymous GET/HEAD/Range, wrong/expired cookies, missing objects, cache headers, successful downloads and mobile/desktop browser behaviour. No public access grants are needed for R2.

## Distribute a paid product

This library distributes paid products to buyers next to the free survey gift. A paid product is a collection of its own in `src/manifest.ts` (`distribution: 'paid-product'`, `audience: 'buyers'`); the current ones are `redmine-clone` (Redmineクローン教材) and `task-app` (Task-App教材). `task-app` (with a hyphen) is a real product; `taskapp` (without one) is only the example of an absent id in the tests, see step 1 below. It is never part of the free gift: the gift phrase does not open a product, and a product phrase does not open the gift. The outer Basic site gate stays in place after distribution starts, so a buyer passes the Basic prompt first and the product phrase second.

This section describes steps; the repository executes none of them. Uploads, secrets and deployment need the same separately approved secure steps as the rest of this runbook. Real URLs, IDs, passwords, phrases and contacts are never written in this repository.

### What a product is made of

| Part | Rule | What checks it |
| --- | --- | --- |
| Phrase setting | A Worker secret named `ACCESS_PHRASE_SHA256_` plus the product `id` in upper case with `-` changed to `_` (`productPhraseEnvName` in `src/manifest.ts`; `ACCESS_PHRASE_SHA256_REDMINE_CLONE` for `redmine-clone`, `ACCESS_PHRASE_SHA256_TASK_APP` for `task-app`). The same name is listed in the `Secrets` type and written in the collection's `phraseEnv`. The value shape and what the Worker does when the secret is unset, malformed or repeats another phrase are in [商品の合言葉（任意）](SETUP.md#商品の合言葉任意). | `npm run typecheck` fails for a `phraseEnv` that is not in `Secrets`. `validateManifest` stops the whole site (503) when `phraseEnv` is missing, differs from the name built from the `id`, or repeats a gift phrase name. |
| Objects in R2 | The private bucket bound as `MATERIALS`. The key of a file is the release `prefix` followed by the material `filename` from the manifest. The prefix is exactly `releases/<id>/<version>/` (`releases/redmine-clone/<version>/` with `redmineCloneRelease.version`, `releases/task-app/<version>/` with `taskAppRelease.version`) and every filename starts with `<id>-` (`redmine-clone-source.zip`, `task-app-curriculum.zip`). Each product also lists an optional textbook, `<id>-textbook.zip` (`textbookMaterial` in `src/manifest.ts`): one ZIP holding the course's Day-by-Day PDFs, in the same prefix. | `validateManifest` (`Invalid release manifest`). The Worker reads only `release.prefix + filename`; a missing object answers with the "preparing" page (404) and a zero-byte object with 503. An optional material (`optional: true`, only the textbook today) is listed on the product page only while a non-empty object is at its key, so the page never shows a textbook link before it is uploaded. The count and label on the `/library` card (`ソースコード一式` vs `教材本文とソースコード`) follow the same rule. `validateManifest` accepts `optional` only on the material with id `textbook`. |
| Approval flag | Each collection has its own approval object (`approval`). For a paid product only `distributionApproved` is read. `productPolicy` is the approval of `redmine-clone` alone and `taskAppPolicy` that of `task-app` alone; both are currently `true`. Another product gets its own object. | `isApproved` in `src/manifest.ts`. `validateManifest` refuses two collections that share one approval object (`Shared approval`). |
| Release state | The product is distributed only when its release has `synthetic: false`, its status is `published` and its approval is `true`. Otherwise the product page shows the preparation state and its downloads answer 503. `distributionApproved: false` closes the product this way in the Worker; shipping that change is not a followable procedure today (see [Closing a product](#closing-a-product)). | `isDistributable` / `canDistributeProduct` in `src/manifest.ts`; the Worker and `npm run release:ready` both call them. |

### The textbook (PDF)

The course text reaches buyers through this site too, behind the same product phrase. For each product, put one ZIP of the Day-by-Day PDFs at `releases/<id>/<version>/<id>-textbook.zip`, next to the source ZIP of the same version. Buyers see it as 教材本文（PDF）一式, listed before the source ZIP, saved as `<id>-textbook-v<version>.zip`, with a sentence telling them to unzip it and read from Day 1. Nothing in the manifest changes when it is uploaded: the product page lists it as soon as a non-empty object is at that key, and hides it while the key is empty or missing. The product repositories' `deploy-r2.yml` upload only the source ZIP today; until they also upload the textbook, the operator uploads it by hand under the same immutability rule (a new version gets a new prefix, never overwrite a served object). `npm run release:ready` reads the manifest only, so it does not report whether the textbook is uploaded.

### What `npm run release:ready` tells you

`npm run release:ready` reads `src/manifest.ts`, runs `validateManifest` and prints one line per collection. Example output, taken with `redmine-clone` at 0.2.1 and `task-app` at 1.1.4 (the version numbers follow the manifest):

```text
survey-gift: blocked typescript 0.2.2-synthetic - synthetic materials, status preview, giftPolicy.myaspVerified is false, giftPolicy.distributionApproved is false
paid-product: ready redmine-clone 0.2.1
paid-product: ready task-app 1.1.4
Note: the survey gift stays closed in production because it is blocked; only the ready collections are released.
Approved manifest is ready for a separately authorized production release.
```

- `paid-product: ready <id> <version>` means the manifest allows production to distribute that product: non-synthetic release, status `published`, approval `true`.
- `paid-product: blocked <id> <version> - <reasons>` names what is missing (`synthetic materials`, `status …`, `no release`, or the approval flag with its current value). A blocked product stays closed in production; it does not stop the release of the others.
- The command exits 1 when no collection is ready, or when the survey gift is approved but cannot be distributed. It also exits non-zero, before printing any line, when `validateManifest` throws (for example `Invalid release manifest` or `Shared approval`). The optional deploy job runs it before deploying.
- It reads the manifest only. It does not look into R2 and does not know whether the phrase secret is set, so `ready` is not proof that the objects are uploaded or that buyers can log in. Check those separately (steps below).

### Start distributing a product

For `redmine-clone` and `task-app` the manifest side of these steps is already in place (`status: 'published'`, `productPolicy.distributionApproved: true` and `taskAppPolicy.distributionApproved: true`). The list is for another product, or for checking the existing ones.

1. Add the collection to `collections` in `src/manifest.ts` with `distribution: 'paid-product'`, `audience: 'buyers'`, its `materials` (filenames starting with `<id>-`), its own release object, named `<id in camelCase>Release` and closed with `} as const;` (`redmineCloneRelease`, `taskAppRelease`; `promote-product.mjs` finds the object only by that name) with `schemaVersion: 1`, `version`, `date`, `synthetic`, `prefix: 'releases/<id>/<version>/'`, the three `verification` sentences) and its own approval object with `distributionApproved: false`. The product page (`productLibrary` in `src/views.ts`) shows the saved file name and, when the collection has a `filenameHint` (`{ filename, day, material }`, where `material` is the id of the non-optional ZIP the rename sentence is about, for example `'source-zip'`), a sentence asking the buyer to rename the file to the name the course's own instructions use from that day on (`redmine-clone.zip` from Day 3 for `redmine-clone`, `task-app-curriculum-v1.1.zip` from Day 1 for `task-app`). Set it for the new product, or leave it out when the course needs no rename. The product also lists `textbookMaterial('<id>')` first in `materials`. Add the phrase setting name to `Secrets` and to `phraseEnv` as described in [商品の合言葉（任意）](SETUP.md#商品の合言葉任意). Update `tests/check-release.test.mjs` in the same change, so that it passes in the state after step 4: several of its tests run the release check on the real manifest (most of them with an edit of their own) and match the `paid-product:` lines and the `Note:` line, or its absence, which counts the blocked collections. While the new product is still blocked (this step) some of them fail; run `npm run check` (not `npm test` alone, which runs the Worker tests against the last build) and read which. In the state after step 4 the test `release check blocks when the survey gift is unapproved and no paid product is ready` fails, because its edit blocks only `productPolicy` and `taskAppPolicy` and the new product stays ready; change that edit so that every paid product, the new one included, is blocked. Tests in `tests/security.test.mjs` that count the catalogue cards (for example `unopenable catalogue cards read as locked and openable collections sort first`, which expects three) need the new count too. The tests also use `taskapp` as the example of an id or filename that does not belong to the manifest (in `tests/security.test.mjs` the filename validation test, the gift-catalogue test, the unknown-id route test and the manifest-mixing test that uses it as an id the gift does not allow, and in `scripts/browser-check.mjs` the unknown-id download check). Before adding a product whose id is `taskapp`, change those checks to an id that stays absent from the manifest; search for `taskapp` to find them all. The local fixtures (`scripts/fixtures.mjs`, used by `npm run dev` and the tests) seed a dummy ZIP for every paid product in the manifest at its release prefix and filename (`productFixtures`), so the new product gets one without a change there. The local phrases are not derived: `scripts/runtime.mjs` defines one per product (`localProductPhrase` for `redmine-clone`, `localTaskAppPhrase` for `task-app`, each different, because two products sharing a digest are closed) and `scripts/dev.mjs` binds and prints them; a local preview of the new product needs its own phrase in both files.
2. Upload the files to the new private prefix `releases/<id>/<version>/` under the manifest filenames. Never overwrite objects of a release that is being served. Compare every object's size and checksum with the private release report.
3. Prepare the product phrase (random, at least 128 bits, different from every other phrase) and place its SHA-256 digest in the product's secret. The value shape and the digest command are in [the setup guide](SETUP.md#本番に必須の設定値). Ordinary `wrangler secret put` deploys immediately; see step 5 of [Before activation](#before-activation).
4. When the release review is recorded privately, set `synthetic: false`, `status: 'published'` and the product's `distributionApproved: true`. Run `npm run check`, then `npm run release:ready` and confirm the line `paid-product: ready <id> <version>`.
5. Deploy that commit through [Deploy and verify](#deploy-and-verify). Through the real hostname, confirm that the product phrase opens `/courses/<id>` and the download, and that the gift phrase does not.
6. Send buyers the notice (see [What the buyer receives](#what-the-buyer-receives)).

### Raise the version of a product

Example: `redmine-clone` from the version being served (called `OLD` below; it is `redmineCloneRelease.version` before the edit) to a new version `X.Y.Z`. For `task-app` the steps are the same with `taskAppRelease`, the prefix `releases/task-app/X.Y.Z/`, the file `task-app-curriculum.zip` (saved as `task-app-curriculum-vX.Y.Z.zip`) and the page `/courses/task-app`, with one more check: the `filenameHint` of `task-app` (`task-app-curriculum-v1.1.zip`, the name the course's Day 1 instructions use) holds a version of its own. Change it, and the literal in `tests/security.test.mjs` that matches the rename sentence, only when the course's instructions use a new name; nothing changes it for you.

Step 2 can also be done by `node scripts/automation/promote-product.mjs --collection <id> --version X.Y.Z [--date YYYY-MM-DD] [--dry-run]`, or by the `promote-product.yml` workflow that runs it and opens a pull request (see [Repository automation](#repository-automation-manual)). It rewrites only `version`, `date` and `prefix` of that product's release constant and runs `validateManifest`; the three `verification` sentences are left as they were, so review them in the same change. It does not upload anything, and merging its pull request does not deploy. The promotion does not carry the textbook over: a promotion PR merged before `<id>-textbook.zip` is uploaded to the new prefix hides the textbook for that version. The script is covered by `tests/automation.test.mjs`; the workflow has never run successfully (see [Repository automation](#repository-automation-manual)), so until it has, use the script by hand.

1. **Upload first.** Put the new files under a new prefix `releases/redmine-clone/X.Y.Z/` with the same filenames as the manifest (`redmine-clone-source.zip`, and `redmine-clone-textbook.zip` when the textbook is distributed; the R2 key carries no version in the filename). The textbook is read from the same new prefix, so a version raise without it hides the textbook for that version until it is uploaded there. Leave `releases/redmine-clone/OLD/` untouched: it is still being served and it is the rollback target. Compare sizes and checksums with the private release report.
2. **Edit `redmineCloneRelease` in `src/manifest.ts`** and nothing else for the version:
   - `version`: `'X.Y.Z'` (lower-case letters, digits, `.` and `-`).
   - `prefix`: `'releases/redmine-clone/X.Y.Z/'`. It must be exactly `releases/<id>/<version>/`, otherwise `validateManifest` throws and the whole site answers 503.
   - `date`: the release date. The product page shows it next to the version.
   - `verification`: the three sentences (`delivery`, `materials`, `platforms`) are shown on the product page as written. Rewrite them so they are true for the new files.
   - The collection's `version` is `redmineCloneRelease.version`, so it follows by itself. `synthetic` stays `false`. `phraseEnv`, the secret and the phrase do not change: the setting name is built from the `id`, not from the version.
   - `productPolicy.distributionApproved` stays `true`. The new version is served from the deploy in step 7 on; until then the deployed commit keeps serving `OLD`, so the order (upload, manifest edit, checks, deploy) is what keeps buyers on a complete release. Setting the flag to `false` is not part of a version raise: step 4 then fails, and step 5 prints the product as `blocked` instead of `ready` (see [Closing a product](#closing-a-product)).
   - Change a `filename` or add a material only when the set of files itself changes; the uploaded object names must then match. `scripts/fixtures.mjs` takes the filename from the manifest, but the tests write it as a literal, so in the same change also update every `redmine-clone-source` in `tests/security.test.mjs` (the object keys put into the test bucket and the expected saved name `redmine-clone-source-v<version>.zip`; for `task-app`, the keys `task-app-curriculum.zip` and the saved name `task-app-curriculum-v<version>.zip`, but not the rename sentence, which follows `filenameHint`). Otherwise step 4 fails even when the manifest and the uploaded objects match, because the tests still put and expect the old name.
3. **What the buyer sees.** `saveName` adds the version to the name of a paid product's ZIP when it is saved: `redmine-clone-source.zip` is saved as `redmine-clone-source-vX.Y.Z.zip`. The product page names that file, and shows the new version and date and the three sentences. Sessions opened before the deploy keep working (up to four hours) and receive the new files after it.
4. **Run `npm run check`.** Nothing in the tests or the local fixtures holds the version as a literal: `scripts/fixtures.mjs` reads each product's release prefix and filenames from the manifest and seeds the dummy ZIP there. (The filename is a literal in the tests; see the `filename` bullet above.) The tests then confirm that the seeded object is at the manifest prefix, that the download is saved as `redmine-clone-source-v<version>.zip`, that the product page shows the version, date and the three sentences, and that a prefix which is not `releases/<id>/<version>/` is refused. When step 2 kept the flag and changed only the fields listed there (plus, for a filename change, the fixture and the tests named above), a failure here means the edit is inconsistent, not that R2 is wrong; the tests never read the production bucket.
5. **Run `npm run release:ready`** and confirm `paid-product: ready redmine-clone X.Y.Z`. A `blocked` line names the reason.
6. **Read the product page locally.** `npm run test:browser` logs in with the gift phrase only and does not open the product page. Start `npm run dev`, enter the local dummy product phrase that the preview prints, and read the version, date, saved file name and the three sentences on `/courses/redmine-clone`. The local ZIP is a dummy; only the page text is being checked here.
7. **Deploy** the reviewed commit through [Deploy and verify](#deploy-and-verify). Deploying before step 1 is complete makes the product download answer with the "preparing" page, because the new prefix has no object yet. After the deploy, confirm through the real hostname that the product phrase downloads `redmine-clone-source-vX.Y.Z.zip` with the expected size.
8. **Roll back** by deploying the previous reviewed commit; its manifest points at `releases/redmine-clone/OLD/`, which step 1 left in place. Do not delete an earlier prefix until the retention decision in [Roll back](#roll-back) is approved.

### Closing a product

This is what is true today; it is not a procedure.

- In the Worker, `distributionApproved: false` on a product's approval closes that product: `/courses/<id>` shows the preparation state and `/download/<id>/…` answers 503 (`canDistributeProduct` in `src/manifest.ts`, called by `src/index.ts`). Another product with its own approval is not affected.
- The tests expect both products to be approved. Measured with `npm run check` on the commit that added this sentence (101 tests in all): with only `productPolicy.distributionApproved: false`, 15 fail, eight in `tests/check-release.test.mjs` and seven in `tests/security.test.mjs` (they open `/courses/redmine-clone` or download its ZIP with the product phrase, also behind the production Basic gate, or assert that the real manifest's approvals allow distribution). With only `taskAppPolicy.distributionApproved: false`, 8 fail, seven in `tests/check-release.test.mjs` and one in `tests/security.test.mjs` (`the Task-App phrase unlocks only Task-App …`). The failing tests in `tests/check-release.test.mjs` either edit the manifest by replacing the text `distributionApproved: true,` under that approval, which is then absent, or expect that product on a `paid-product: ready` line and a `Note:` line (or none) that does not count it as closed. The counts change whenever tests are added; run `npm run check` for the current ones. `npm test` alone runs the Worker tests against the last `dist/index.js`, so without `npm run build` first it misses the change to the manifest and reports fewer failures.
- `npm run release:ready` still exits 0 while the other product is ready: it prints the closed product as `paid-product: blocked <id> <version> - <policy>.distributionApproved is false` and adds a `Note:` line saying it stays closed. Only when both products are closed (and the survey gift is blocked too) does it exit 1 with `Release blocked: no collection is distributable (survey gift and paid product blocked)`. The deploy job runs this command before deploying, and [Deploy and verify](#deploy-and-verify) needs verification to pass for the same commit.

So there is no followable way to deploy a closed product without first changing those tests, and this runbook does not define that change.

### What the buyer receives

- A notice written from [the notice template](notice-template.md): section 1 for a first purchase, section 2 for a buyer who already holds another product. The sender fills in the entry URL, the product phrase, the product name and the contact, and for section 1 also the Basic ID and password (section 2 tells the buyer to reuse the ones already received). Those values are never written in this repository.
- On the site: the product page `/courses/<id>` and the download, saved under the versioned name described above.
- The channel and the timing by which buyers receive that notice (and with it the phrase) are decided by the operator and are deliberately not written in this public repository.

## CI/CD activation (not performed)

Every workflow currently checked in can be started with `workflow_dispatch`, and `promote-product.yml` also answers `repository_dispatch` of type `product-release`; no other trigger is used. The local test (`tests/automation.test.mjs`) fails when a trigger is added or when any workflow other than `promote-product.yml` gains `repository_dispatch`; it does not prevent a newly added PR-triggered workflow from running before that test. Review trigger changes before pushing. No Actions run has been dispatched; the only run recorded apart from Dependabot updates is a failed `push`-event entry for `promote-product.yml` on 2026-11-16. Before first manual execution, verify the actual plan and free usage limits and review this configuration. `npm run check` needs `pdfinfo`/`pdftotext` (poppler), which the runner image does not list, so `verify.yml` and `promote-product.yml` install `poppler-utils` with apt before `npm ci` (`tests/automation.test.mjs` fails when a workflow runs `npm run check` without that step before it); neither workflow has been run on GitHub since that step was added. It uses `ubuntu-latest`, no self-hosted/larger runners, no artifact storage, and no cache storage. Concurrency is fixed for the library and cancellation is disabled, so verification and deployment from different releases cannot race. `promote-product.yml` has its own concurrency group (`promote-product`), also without cancellation, so two promotions do not edit the manifest at the same time.

Only if recurring GitHub CD is separately authorized, confirm the actual token policy and secure destination before creating or storing a credential. Legacy `Workers Scripts Edit/Write` is account-scoped; do not describe it as limited to one named Worker. New individual-Worker Editor authorization is documented separately, but its actual availability and policy on the target account remain unverified. After that approval, place the credential and account ID in the `production` environment secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Set environment variable `CLOUDFLARE_SETUP_VERIFIED=true` only after plan/limit, bucket privacy, secrets, hostname, and material verification are complete. The optional deploy job uses the same `github.sha` as verification and refuses a placeholder production configuration. Environment-level approval protection should be configured separately if authorized; this runbook creates no grants or credentials.

## Repository automation (manual)

These workflows use the run's `GITHUB_TOKEN` and require no new credential. Operators must select a trusted, reviewed branch for manual dispatch (a `repository_dispatch` to `promote-product.yml` runs the default branch's version): checkout-based workflows execute the selected branch's scripts, sometimes with write permissions. Selecting an untrusted PR branch would execute its code with that token. The public-content check reads target text via API rather than checking out target PR code. Their decisions live in `scripts/automation/` and are unit-tested in `tests/automation.test.mjs` with a fake API, so no test issue or comment is written to this public repository.

- `public-content.yml` (inputs: `issue`, `pr`, `issue_comment` or `review_comment` and the number or comment id): checks the title/body against `.github/public-content-rules.json` (or the file named by `PUBLIC_CONTENT_RULES`). On a hit it turns red and keeps one marked comment with the rule name, line numbers and counts only, never the matched text; it never edits or deletes the checked text. The checked-in rules are a placeholder baseline (tokens, private-key blocks, secret assignments, database URLs, personal email); the real rule list (secret names, weakness/attack steps, database names and IDs, customer names and amounts, forbidden words) must come from the requester on issue #8 and replace that file.
- `body-format.yml` (inputs: `issue`/`pr` and number): checks the five issue headings (背景 / 今どこまで / 次にやること / 誰の判断待ち / 完了条件) or the PR headings (概要 / 変更内容 / 関連Issue with `Closes #n` or `Refs #n`; the account default template's 概要・背景・妥協点 / やったこと / 関連 Issue are accepted). It keeps one marked comment, updates it to OK after a fix, and skips bots, draft PRs and `alert` issues.
- `issue-heading-fix.yml` (input: issue number): changes `###` to `##` and `####` to `###` outside code blocks, and edits the issue only when the text would change.
- Templates: `.github/ISSUE_TEMPLATE/request.yml` makes the five checked headings required. ## Deploy and verify

1. Select a reviewed commit and the optional deployment input only after the above prerequisites are met. Verification must pass for that same SHA before deployment.
2. Record the Git SHA, content manifest version, Cloudflare Worker version ID and previous Worker version ID in private release evidence. Use the stable entry URL in the newsletter; MyASP configuration remains unchanged.
3. Repeat the anonymous/authenticated/cache-isolation checks through the real HTTPS hostname. Confirm `r2.dev` and public bucket domains remain disabled. A code test cannot establish account-level privacy or billing settings.

## Roll back

1. If credentials or materials leaked, rotate the access phrase and session signing secret through the approved secure flow; rollback alone does not revoke sessions or downloaded files.
2. Revert the manifest/application to the previous known-good reviewed commit through normal review and deploy after same-commit verification, or use the approved Cloudflare Worker version rollback for an urgent application rollback. Match the Worker version to its embedded material manifest.
3. Keep the previous immutable R2 objects available. Validate the stable URL and authentication/download/cache behaviour again. Do not delete releases until the recovery/retention decision is separately approved.
